04 / 05

Hero investigation flow

Evidence → decision → rationale → trace.

The core Sentry journey keeps an analyst inside one split workspace from alert selection to committed outcome. The goal is not maximum speed at any cost; it is reducing context switching while preserving enough evidence and accountability for a defensible decision.

ActorFraud / risk analyst
ScenarioHigh-risk ATO signal
OutcomeAuditable disposition
04.01

Normal flow

A selected alert stays anchored while evidence, action and audit context change around it.

1 · Select alert

Pick prioritized item from queue; risk reason and age remain visible.

→
2 · Inspect evidence

Review risk gauge, transaction velocity, geo hop, device and beneficiary signals.

→
3 · Compare history

Check current behavior against prior account baseline and linked entities.

→
4 · Choose action

Block, allow, verify, escalate or mark false positive.

→
5 · Add rationale

Apply categorical tags and enough notes for independent review.

→
6 · Commit & advance

Write audit record, update state and move to next priority item.

04.02

Scenario walkthrough

The prototype’s flagship scenario combines multiple weak signals into a stronger correlated risk picture.

Trigger

ALT-8921 · 94 / 100

A new payment event arrives with impossible travel, first-seen device behavior and unusual beneficiary context.

Correlate

Cross-signal evidence

Device fingerprint contradicts claimed environment; geolocation delta is physically implausible; velocity departs from the account baseline.

Decision

Block & freeze

Analyst chooses a protective action only after evidence inspection, then records tags and justification before commit.

04.03

Rule conflict branch

Automation disagreement is not silently resolved. Sentry exposes the conflict and hands precedence to an authorized analyst.

Triggered rule

Rule 301: foreign luxury payment → hold.

+
Exemption

Rule 012: trusted VIP profile → allow.

→
Conflict detected

System explains both conclusions and blocks silent auto-resolution.

→
Analyst precedence

Choose governing rule and record rationale.

→
Audit

Decision stores both rule inputs plus the human resolution.

04.04

Verification branch

When evidence is ambiguous, the analyst can request more proof instead of forcing allow/freeze too early.

SUCCESS

2FA verified

Challenge succeeds; verification evidence is attached and analyst resumes review with stronger identity confidence.

FAILED

2FA failed

Failure becomes additional evidence. The same alert reopens with freeze and escalation paths available.

EXPIRED

Challenge expired

Timeout is shown as its own state; it is not interpreted as a failed identity proof without evidence.

04.05

False-positive branch

Clearing an alert is still a high-value decision because it affects customer friction and future review patterns.

Evidence review

Signals initially appear risky.

→
Baseline match

Travel, device or beneficiary becomes explainable through history.

→
False positive

Analyst explicitly clears the alert rather than simply closing it.

→
Feedback trace

Reason is preserved for later rule and model evaluation.

04.06

Operational recovery

The most important failure mode is losing a decision after the analyst believes it has been committed.

SAVE ERROR

Audit write fails

Keep the selected alert and entered rationale intact. Block auto-advance and expose a safe retry.

SOURCE DOWN

Evidence provider unavailable

Mark the missing source explicitly; do not collapse “unknown” into “clean”. Allow escalation or deferment.

PERMISSION

Action not authorized

Explain which role can complete the action and preserve the analyst’s evidence review for handoff.
